# Issue: единый контракт валидации форм

## Источник идеи

В legacy `js/components/validation.js` есть полезные поведенческие паттерны. Их
нужно перенести как отдельную form-инфраструктуру, а не как часть компонентов
RepUI и не вместе со старым runtime.

## Целевое поведение

- использовать нативный `ValidityState` и browser validation как источник истины;
- подключать валидацию явно к форме, например через `data-rui-validate`;
- показывать ошибку только после `blur`, `input`/`change` или submit;
- при submit помечать все поля проверенными и фокусировать первое невалидное поле;
- выставлять `aria-invalid="true|false"`;
- связывать поле с описанием и ошибкой через `aria-describedby`;
- использовать `setCustomValidity()` для серверных ошибок;
- очищать серверную ошибку при следующем изменении значения, если она не помечена
  как persistent;
- поддерживать локализованные сообщения для стандартных причин:
  `valueMissing`, `typeMismatch`, `tooShort`, `tooLong`, `patternMismatch`,
  `rangeUnderflow`, `rangeOverflow`, `stepMismatch` и `badInput`;
- позволять переопределить сообщение на конкретном input через `data-rui-message-*`;
- корректно сбрасывать состояние после native reset;
- быть идемпотентным и иметь явный `destroy()`/cleanup для HTMX lifecycle.

## Архитектурные ограничения

- не переносить legacy `validation.js` целиком;
- не добавлять validation runtime внутрь Button, Input, Select или Choice;
- не подменять native form submission и browser semantics без необходимости;
- серверные ошибки должны поступать явно из Django/HTMX response;
- сообщения ошибок должны экранироваться как обычный текст;
- компонентные стили должны использовать общий контракт цветов и typography tokens.

## Минимальные проверки

- required input показывает ошибку после submit;
- ошибка исчезает после исправления значения;
- серверная ошибка отображается и попадает в `setCustomValidity()`;
- `aria-invalid` и `aria-describedby` синхронизированы с видимой ошибкой;
- focus переходит на первое невалидное поле;
- reset очищает ошибки и touched-state;
- повторный mount после HTMX не добавляет дублирующие обработчики;
- destroy удаляет обработчики и временные сообщения.

## Следующий шаг

Реализовать отдельный небольшой `forms/validation.js` после появления реального
сценария Django forms/HTMX. До этого legacy validation не подключать и не
сохранять как скрытую совместимость.
