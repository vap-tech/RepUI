# Временный план миграции из `old`

Этот документ нужен только на период переноса legacy-реализаций в текущую
архитектуру RepUI. После завершения миграции файл удалить.

## Правила

- Переносим поведение и полезные behavior specs, а не legacy-код целиком.
- Не переносим старую систему `mount/runtime`, `rui-core` bundle и дублирующие
  DOM/helpers.
- Новый компонент должен использовать текущие публичные tags, tokens, Layout и
  `OverlayPortal`.
- До удаления legacy новая реализация должна иметь Workbench-страницу,
  документацию и минимальные автоматические тесты.
- После ручной проверки удаляем старые исходники, а не сохраняем скрытую
  совместимость.

## Очередь проверки

Эти legacy-реализации пока не удалять: текущие версии отсутствуют или заметно
проще старых.

- `Tabs` — стабилизировать текущий runtime.
- `Combobox` — текущая версия заглушка, сравнить с legacy.
- `Sheet` — текущая версия заглушка, сравнить с legacy.
- `Dropdown` — решить между отдельным компонентом и `Menu + Popover`.
- `AlertDialog` — собрать поверх текущего `Dialog`.
- `Menubar` — добавить runtime только при необходимости.
- `NavigationMenu` — проверять последним, если понадобится desktop submenu.

Остальные legacy-реализации, уже заменённые текущими компонентами, удалять.

## Не переносить

- `old/js/runtime/*` целиком;
- `old/js/vendor/rui-core.min.js`;
- старые Select, Dropdown и Popover целиком;
- старый `validation.js` как часть UI-компонентов;
- старые Django tags целиком;
- старые browser-specific workaround без подтверждённого контракта.

## Удаление `old`

После того как все нужные кандидаты перенесены:

1. пройти `rg` по проекту и убедиться, что текущий код не импортирует `old`;
2. проверить Workbench, `manage.py check` и тесты;
3. удалить использованные legacy-источники;
4. удалить весь `old`, когда в нём не останется нужной спецификации или asset;
5. удалить этот документ последним.
